# OpenViking 集成目标与实施方案

## 1. 目标与定位

采用“全局 Evolve CLI + OpenViking 共享资产 + 项目本地执行副本”的结构：CLI 作为执行引擎独立升级，项目 Skill、已发布 Wiki 和共享记忆由 OpenViking 保存，本地负责治理、固定版本、执行和验证。

这里的“进化”是依据执行证据修改 Skill 文档及其配套文件，不是训练模型权重，也不是自动升级 npm 包。OpenViking 负责保存、管理和召回资产，Evolve 负责决定是否修改、验证修改是否有效，以及是否允许发布。

本文是 OpenViking 项目资产接入的实现契约。前期兼容性依据保留在 [OpenViking 接入兼容性与最小改造评估](openviking-integration-assessment.md)；当前 Session 同步、受控发布与可选本地回退行为以本文和 `OPENVIKING_项目资产_PLAN.md` 为准。

### 可拔插后端与故障策略

没有 `.evolve/openviking.json` 时保持原本地模式，不读取 OpenViking 凭据，也不增加网络或模型调用。显式初始化后启用远端：

```bash
evolve openviking init --policy evolution.json
evolve openviking config --enabled false
evolve openviking config --enabled true --failure-policy local
evolve openviking config --failure-policy fail
evolve openviking status
```

- 连接只读取绝对路径环境变量 `EVOLVE_OPENVIKING_CONFIG` 指定的文件，或 `~/.openviking/ovcli.conf` 的 `url`、`api_key`。项目描述不保存凭据。
- `enabled: false` 关闭新查询与新 Session 的远端接入；默认 `failure_policy: local` 在服务不可达、服务端故障或限流时显式回退本地。`fail` 要求远端可用。响应中的 `knowledge_backend` 标明实际后端和回退原因。
- 已固定远端版本的 Session 不切换 Skill 或 Wiki 约束；优先使用该版本的已验证缓存。远端 Memory 的 `ov:<release>:<origin>` ID 不映射成本地同名记录，缓存缺失时明确失败。
- 身份不匹配、非法路径、哈希错误、未审批 Wiki 和发布冲突不适用可用性回退。回退不会伪造远端发布成功。
- 业务 Session 完成后，远端暂不可用不撤销业务完成；保留失败的 publication 和 `openviking finish` 恢复命令。显式 `openviking sync`、`finish` 仍报告未完成的远端操作。
- `memory put/extract/sync/delete` 保持本地写入；用 `openviking memory share|unshare <local-id>` 明确选择下次发布的正文，取消分享保留 tombstone。查询可用 `--memory-backend local` 显式选择本地读取。
- Memory 的 `--session` 仍是历史过滤条件；`--workflow-session` 固定当前 Evolve Session。`context` 和 Wiki 只读命令使用 `--session`，`--reads` 的伴随文件固定搜索与精读的 release。

### 核心目标

1. 全局安装 Evolve CLI，不在每个项目中维护一份执行引擎。
2. OpenViking 保存各项目的完整 Skill 副本及其进化版本，项目之间相互隔离。
3. 每个 Evolve Session 开始时，同步最新已发布 Skill，并在整个 Session 内固定版本。
4. Session 结束时按证据判断是否需要进化；只有经过隔离回放、合并和验证的修改才允许发布。
5. Memory/Wiki 接入远端共享知识，保留本项目的正式约束治理、精确值保护和证据机制。
6. 多台机器共享逻辑资产，而不是共享 SQLite 文件、Git 工作区或正在运行的 Session 状态。
7. 尽量复用公开接口、保留本地模式，不修改 TencentDB 复用算法或上游依赖来迁就集成。

## 2. 数据与职责分工

| 对象 | 共享与存储职责 | 本地保留职责 |
|---|---|---|
| Evolve CLI | 通过独立的软件包安装和升级 | 提供命令、状态控制、执行与验证能力 |
| 项目 Skill | OpenViking 保存完整发布包、版本和来源 | 物化项目副本，纳入现有 Git 版本绑定，执行固定版本 |
| 共享 Memory | OpenViking 保存已发布记忆并提供召回 | 源消息接地、精确值核对、读取证据、固定快照与缓存 |
| 已发布 Wiki | OpenViking 保存共享正文及治理元数据 | 按状态与作用域计算适用约束，执行提案、应用与校验 |
| Session / Run | 不用 OpenViking Session 替代 Evolve 状态机 | 本地数据库、Run 制品、读取回执、恢复与执行现场 |
| CodeGraph | 不用资源检索替代准确的代码图 | 保留现有本地索引、调用关系和路径追踪 |

OpenViking 是已发布共享资产的主存储，本地 SQLite/FTS 和 Markdown 副本承担运行状态、来源证据、Session 快照与缓存，不再作为另一套需要独立双写的跨机知识真源。

OpenViking Session 用于它自己的消息、记忆提取和轨迹关联；Evolve Session / Run 用于任务执行治理。两者可以关联，但不是同一套状态机。

## 3. CLI、上游基线与项目版本

必须区分三类版本：

- **CLI 版本**：执行引擎及其命令实现的版本。
- **上游 Skill 基线**：项目副本所继承的原始 Skill 包版本。
- **项目进化版本**：在基线之上，经过证据归因与验证后形成的项目修改。

CLI 升级不能隐式覆盖已经进化的项目 Skill。同步与发布的单位是完整 Skill 包，包含 `SKILL.md`、references、scripts 及其他依赖文件，不能只更新入口 Markdown。

本地执行沿用现有项目安装和 Git 绑定机制；安装路径与脚本入口需要在实现时依据 CLI 当前行为核对，不额外发明第二套 Skill 目录约定。

## 4. Session 开始：同步并固定版本

每个新 Evolve Session 按以下顺序准备运行输入：

1. 读取稳定的项目身份与远端资产绑定，确认访问范围。
2. 获取该项目最新、完整、已发布的 Skill 版本及其元数据。
3. 校验包内容、依赖文件、来源、版本和内容哈希。
4. 检查本地 Skill 修改和版本基线；不能覆盖未合并的本地改动。
5. 将通过校验的包物化到项目目录，并按现有机制形成可绑定的 Git 版本。
6. 固定本 Session 使用的 Skill 版本和知识快照，随后分配、执行 Run。

同一 Session 中，远端后续发布不改变已固定输入。新的发布由后续 Session 获取，不能让当前执行链中途漂移。

获取失败、包不完整、权限不符或本地存在冲突时，不得把同步标记为成功。已固定的 Session 可以继续使用自己的已验证快照；新 Session 不得悄悄使用过期缓存冒充“最新版本”。

启动同步同时校验已提交的本地 Skill 内容与上次物化基线，避免把 clean working tree 误当成没有本地改动。新机器首次同步会确认其对应的已发布祖先版本，并处理该版本的文件删除；无法对应已发布基线、或已有基线后的本地内容/删除冲突，返回 `OPENVIKING_LOCAL_ASSET_CONFLICT`，不覆盖本地提交、不推进 Session 到 ready。

## 5. Session 结束：按证据进化并发布

### 5.1 归因与候选修改

- 收集本次执行中的失败、纠正、重试和经过验证的修复，关联实际读取的 Skill 与知识。
- 区分 Skill 缺陷、执行器缺陷、模型输出问题、依赖故障和环境问题。
- 只有能归因到 Skill 且有可追溯证据的信号才形成候选；没有有效信号时保持零修改、零发布。
- 最小修改实际相关的 Skill 文档或依赖文件，不扩大到无关行为。

### 5.2 隔离回放与合并

1. 固定原始基线、候选 Skill 和知识输入。
2. 在隔离工作区运行基线与候选场景。
3. 验证原有通过路径没有回退、目标失败得到修复；验证应覆盖实际任务行为，而不只比较一段预期字符串。
4. 检查远端是否出现其他机器发布的新版本。
5. 若需要合并，使用共同基线进行三方合并，并对合并结果重新执行回放。
6. 仅将已经验证的最终内容合入本地执行版本。

基线与候选必须使用同一份知识快照，避免把远端知识变化误判为 Skill 修改的效果。不能把普通外部异常当成“已自动回滚”；回滚是否完成必须有实际执行结果。

### 5.3 发布与恢复

- 发布完整包和可核对的来源、基线、内容哈希及验证引用。
- 明确区分上传完成、处理/索引完成和发布可用，不能只凭一次 HTTP 成功认定另一台机器已经能够读取。
- 未完成或失败的发布不能成为“最新已发布版本”。
- 并发更新不能以最后写入覆盖解决；无法安全合并时保留已发布版本并明确返回冲突。
- 不假设远端原位更新具备跨文件原子事务、条件更新或自动回滚；发布协议必须在核对真实 API 后确定。
- 记录恢复所需的本地版本和远端引用，区分未发布候选与可供新 Session 使用的正式发布。

## 6. Memory 与 Wiki 的能力融合

### 6.1 比较对象与重复能力

本节比较的是本仓库内嵌、改造后的 TencentDB Agent Memory 部分，不是断言 TencentDB 产品整体只能在本地使用。

已有实现与 OpenViking 在记忆抽取、摘要、长期存储、文档处理和检索方面存在明显重叠。融合目标是统一共享资产与召回入口，不是同时维护两套独立抽取、再彼此导入的记忆库。

以下能力不能因为迁移存储就删除：

- 原始消息定位与来源引用。
- 大小写、前导零、符号等精确值保护。
- 读取回执和内容哈希。
- Wiki 的状态、适用范围及发布治理。
- Run 制品、Git 固定和隔离回放证据。

### 6.2 Memory：统一召回与精读

- CLI 和 Run MCP 使用一致的数据源适配边界。
- 搜索命中的远端记录必须从对应来源精读，不能再从本地读取一个同名 ID。
- 保留远端 URI、正文、内容哈希和来源信息；检索摘要不能冒充已读取的原文。
- 同一源事件走一条明确的抽取、审查与发布链，避免重复提取、循环摘要和回灌。
- 语义召回不能替代精确标识和原始消息核对。
- 原有本地读取回执只能证明实际发生的本地读取；远端获取与本地快照读取分别保留证据，不能伪造为同一次操作。

### 6.3 Wiki：共享正文，保留治理

优先使用已批准发布快照，将正文连同 `mode`、`status`、`scope`、repository/task/path 等适用信息一起保存和同步。

- 正式约束继续按确定性作用域和状态规则计算，不能靠语义 top-k 决定是否生效。
- 远端来源未经审查时先作为参考或候选，不能直接成为 binding constraint。
- 导入和发布经过现有提案、应用及校验入口，不直接改写 `wiki/entries/` 或运行数据库。
- 已废弃、已删除或失效的知识必须反映到本地副本，避免旧缓存永久有效。
- 不必先将现有同步文件扫描整体改成网络调用；受控本地快照负责稳定执行，远端负责共享发布。

## 7. 多机共享、隔离与权限

1. **项目身份稳定**：使用稳定项目 ID 关联资产，不能使用某台电脑的绝对路径作为跨机器身份。
2. **逻辑同步**：交换内容、版本和元数据，不复制正在使用的 SQLite 文件。
3. **项目隔离**：项目 A 的同步、检索和发布不能读错或覆盖项目 B 的 Skill 与知识。
4. **权限边界明确**：同一用户多机共享不等于团队共享；私人 memories 不默认进入团队库。
5. **发布内容受控**：不自动上传整个工作区、原始私有对话或凭据，只发布明确选择的项目资产和允许共享的来源证据。
6. **并发可检测**：记录共同基线和发布来源，拒绝未经验证的覆盖；并发冲突必须显式处理。
7. **回放可复现**：保留实际使用的 Skill、知识快照和内容引用，不以稍后更新的远端内容重建过去的输入。

## 8. 与上游升级的兼容策略

- 不直接修改 `src/upstream/`、`dist`、`node_modules` 或全局已安装包来接入服务。
- 优先依赖公开 CLI、包导出和 OpenViking HTTP API；将远端差异集中在小范围适配层。
- 复用现有提案、应用、读取回执与 Skill 版本绑定机制，不增加平行治理约定。
- 保留明确选择的 local backend，不把远端失败悄悄隐藏为本地成功。
- CLI、上游 Skill 基线和项目进化版本分别升级，基于共同基线合并项目修改。
- 用契约验证约束升级边界，不承诺任何未来破坏性更新都无需适配。

## 9. 实施顺序

1. 在新分支工作；保留现有用户改动，最多使用一个子代理。
2. 恢复本地 CLI 构建与项目知识门禁，读取治理知识并建立对应 Session / Run。
3. 核对服务版本、身份权限、完整包导入/导出、内容完整性和并发发布能力。
4. 实现项目绑定、完整包传输、发布版本和来源记录。
5. 接入 Session 开始时的同步、冲突检查与 Git 版本固定。
6. 接入 Session 结束后的证据归因、隔离回放、三方合并与验证后发布。
7. 接入 CLI / Run MCP 的 Memory 搜索及精读、Wiki 受控快照与失效同步。
8. 进行隔离安装和真实服务端联调，验证跨项目、跨 Session 与跨机行为。

第一次安装和联调使用隔离的安装位置及远端项目副本，不覆盖现有全局 CLI、既有 Skill 或生产项目资产。完成验证后再执行正式环境切换。

## 10. 行为验收目标

| 场景 | 必须观察到的结果 |
|---|---|
| 两个不同项目同步与发布 | 各自只读取、修改自己的项目资产 |
| Session A 固定后远端发布新版本 | A 保持原版本，后续 Session B 获取新版本 |
| 下载缺文件、哈希不符或读取失败 | 不替换可用本地版本，不声称同步成功 |
| 本地有修改或远端并发更新 | 不直接覆盖；合并结果重新回放，冲突明确暴露 |
| 没有可归因的进化信号 | 不生成新 Skill 版本，不产生无意义发布 |
| 候选或合并结果验证失败 | 不进入已发布版本，原有版本保持可用 |
| CLI 与 Run MCP 查询同一 Memory | 能精读对应正文，来源与哈希可核对 |
| Wiki 废弃或不属于当前作用域 | 不作为当前正式约束生效 |
| 适用的正式 Wiki 约束未被语义检索命中 | 仍按治理与作用域规则加载，不依赖语义排名 |
| CLI 升级 | 项目进化 Skill 不被隐式覆盖，本地模式保持可用 |
| 发布中断或索引尚未完成 | 不误报为可供新 Session 使用的完整发布 |
| 隔离安装与服务端联调 | 不改变既有全局安装和生产资产 |

## 11. 实现前需要核对的接口事实

以下内容必须依据当前源码和实际服务确认后，写入可执行的代码改造计划；本文不预设未经核对的命令、配置字段或 API 保证：

- 全局 CLI 安装后，Skill scripts 如何解析 CLI 与依赖路径。
- OpenViking 完整 Skill 包的导入、导出及辅助文件保留规则。
- 包的 revision、逐文件哈希与完整性元数据的实际返回范围。
- 项目隔离与 URI 命名空间的权限约束。
- 并发发布、不可变版本、处理完成和恢复能力。
- 搜索与精读数据源的类型接缝、现有读取回执允许的扩展方式。
- 已批准 Wiki 快照经过治理入口落地的具体调用路径。

官方核对入口：

- [Skills](https://docs.openviking.ai/en/api/04-skills)
- [OVPack](https://docs.openviking.ai/en/api/14-ovpack)
- [Memory](https://docs.openviking.ai/en/api/16-memory)
- [Agent Evolution](https://docs.openviking.ai/en/api/19-agent-evolution)

OpenViking 的 Experience 读取与结果轨迹关联可用于复盘，但关联不等于因果证明，也不替代 Evolve 对候选修改的隔离回放和行为验证。
